SpacetimeDB powers Gunbound's real-time multiplayer backend: player identity, lobby rooms, matchmaking, friends, chat, and deterministic round replay.

## Key Concepts

**Identity-based architecture** — Every player has a permanent SpacetimeDB `Identity`. Rows link to it across sessions and devices.

**Live subscriptions** — React hooks subscribe to tables (or filtered queries) and re-render when rows change. No polling.

**Server-side reducers** — All mutations go through deterministic reducer functions on the server module.

**Token-based persistence** — After login, the session token is stored in `localStorage` and encrypted in the public `credential` table for cross-device recovery.

## Tables (current)

| Table | Purpose |
| --- | --- |
| `player` | Profile, XP, level, presence, admin flag |
| `credential` | Encrypted session tokens for login |
| `room` | Lobby / match container (2-player rooms) |
| `room_member` | Who is in a room, mobile pick, ready state |
| `round` | One played match inside a room |
| `round_event` | Append-only battle event stream for replay |
| `round_stat` | Per-player stats submitted after a round |
| `chat_message` | In-room chat |
| `lobby_chat_message` | Public lobby channel chat |
| `friend_request` / `friendship` | Buddy list |
| `room_invite` | Room invitations |
| `waiting_player` | Matchmaking queue |
| `app_setting` | Runtime feature flags (public) |

Social tables use **client visibility filters** so each subscriber only receives rows where they are a party (requester, recipient, or owner).

## Reducer groups

| Area | Reducers |
| --- | --- |
| Auth | `registerCredential`, `updateCredentialToken` |
| Profile | `setPlayerProfile`, `setPlayerName`, `setPlayerCountry`, `setLobbyPresence` |
| Rooms | `createRoom`, `updateRoomSettings`, `joinRoomByCode`, `leaveRoom`, `kickFromRoom` |
| Match flow | `selectMobile`, `setReady`, `startRound`, `recordRoundEvent`, `submitRoundStats`, `endRound` |
| Chat | `sendChat`, `sendLobbyChat` |
| Social | `sendFriendRequest`, `respondFriendRequest`, `removeFriend`, `sendRoomInvite`, `respondRoomInvite` |
| Matchmaking | `joinQueue`, `leaveQueue` |

Reducer names are snake_case in the module and camelCase on the client (`create_room` → `createRoom`).

## Typical flows

### Sign up
1. Client connects with a fresh token.
2. `onClientConnected` creates a `player` row (empty name).
3. User registers username + password; client encrypts the token and calls `registerCredential`.
4. Token and username are stored in `localStorage`.

### Login on another device
1. Client reads the `credential` row for the username.
2. Client decrypts the token locally with the password.
3. Home screen bumps `spacetimeSessionKey` to remount the provider with the recovered token.

### Play a match
1. Create or join a room (`createRoom`, `joinRoomByCode`, or `joinQueue`).
2. Pick mobile, toggle ready; host calls `startRound` with a seed.
3. Battle actions call `recordRoundEvent`; stats call `submitRoundStats`; host calls `endRound`.

Room status lifecycle: `waiting` → `in_match` → `waiting` (another round) or `ended`.
